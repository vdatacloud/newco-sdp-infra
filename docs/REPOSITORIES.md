# Repositories

How the SDP code is split across repositories, which way dependencies run, and where to find each kind of thing.

> **One map, several copies.** The source is `docs/REPOSITORIES.md` in
> [`newco-sdp-core`](https://github.com/vdatacloud/newco-sdp-core/blob/main/docs/REPOSITORIES.md). Every other SDP
> repo carries a byte-identical copy at the same path so its own graphify graph knows the system's shape. Edit the
> map in core only; the `repo-policy` workflow in each other repo fails when its copy drifts, and the fix is to copy
> core's file over. The same holds for the other shared files: the `github-ci` skill, the PR template and
> `repo-policy.yml` itself. Links here are absolute so they work from any copy.

## The repos

## Which way dependencies run

```
portal, ingest, reporting  ──>  newco-sdp-sdks  ──generated from──>  newco-sdp-core/proto
                                                                           │
newco-sdp-infra  ──provisions and runs──>  everything above                 └─> core services (locker, engine, harness)
```

- Higher-level services (portal, ingest, reporting) reach core only through the SDKs. They never import a core Go
  module and never hold storage or database credentials for tenant data.
- `proto/` in core is the contract. A breaking change goes to a new package version (`locker.v2`) beside the old one;
  the SDKs regenerate from a tagged core release.
- Inside core, services share code only through `commons`, released before the module that needs it.
- Infra depends on nothing in the app repos except published images and charts.

## Working across repos

Clone the repos side by side; core's tooling and agent docs expect the siblings at `../newco-sdp-<name>`:

```
work/
  newco-sdp-core/
  newco-sdp-infra/
  newco-sdp-sdks/
  newco-sdp-portal/
```

Cite plan phases by ID in commits and PRs in any repo (`L4`, `SL1`); IDs are unique across all repos. Each repo has
its own graphify graph, regenerated by CI on `main`; this map is how one repo's graph learns about the others.

## Changing this map

Edit `docs/REPOSITORIES.md` in core and merge it. Then copy the file unchanged into each other repo (one small PR
each, or with the next batch). Until then, each repo's `repo-policy` check reports drift. Never put client data,
tenant names or game titles here: it is sent to a model to build the graph.
